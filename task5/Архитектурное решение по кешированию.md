# Архитектурное решение по кешированию

## 1. Анализ
Проблема:Операторы MES долго ждут загрузки дашборда со списком заказов
Причина Сложный SQL запрос с фильтрацией по статусам и джойнами,выполняемый каждый раз при обновлении страницы
Цель:Закешировать списки заказов для операторов

## 2. Мотивация
Внедрение кеширования снизит нагрузку на `MES DB` (PostgreSQL) и уменьшит время ответа страницы списка заказов с 2-3 секунд до<100 мс
Кешируем
*   Списки заказов 
*   Справочники 

## 3. Предлагаемое решение
**Тип:** Серверное кеширование
**Технология:** Redis 
**Паттерн:** **Cache-Aside** 

Решение 1:Cache-Aside (Выбрано)

Описание:Приложение само проверяет кеш.Если пусто идет в БД и пишет в кеш
+:Устойчив к падению Redis.Гибкий TTL.Прост для чтения
-:Возможно получение старых данных,если не настроена инвалидация

Решение 2: Write-Through
Описание: Приложение пишет всегда в кеш, а кеш сам синхронно пишет в БД
+:Данные в кеше всегда свежие
-:Запись медленнее.Сложно внедрить в существующий код.Требует поддержки со стороны кеш-провайдера

Заключение:
Нам важнее скорость чтения и лучше лучше подходит Cache-Aside
