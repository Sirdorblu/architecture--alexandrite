## 1. Анализ и покрытие
Необходимо покрыть трейсингом весь путь заказа
**Системы:** Shop API -> RabbitMQ -> CRM API / MES API -> Database
**Места разрывов:** Очередь RabbitMQ.Без передачи контекста связь теряется

Данные для трейсинга:
*   `trace_id` (генерируется при создании заказа)
*   Тэги: `order_id`, `client_id`, `status`.

## 2. Мотивация
*   **Бизнес:** Быстрый поиск потерянных заказов. Снижение времени ответа поддержки
*   **Технически:** Обнаружение узких мест 
*   **Метрики:** Снижение MTTR  инцидентов с заказами

## 3. Предлагаемое решение
Используем стек **OpenTelemetry (OTel)** + **Jaeger**.

*   **Агенты:** Внедряем OTel Agents в Java  и OTel SDK в C#.
*   **Контекст:** Используем W3C TraceContext при отправке сообщений в RabbitMQ 
*   **Инфраструктура:** Jaeger All-in-One для старта,Elasticsearch для долгосрочного хранения

## 4. Компромиссы
*   **Performance:** Трейсинг создает нагрузку.Будем использовать **Sampling**,записывая только 10% успешных запросов и 100% ошибочных.
*   **Storage:** Трейсы занимают место. Настроим Retention Policy на 14 дней

## 5. Безопасность
*   Не логировать в теги пд,токены карт и пароли.
*   Доступ к Jaeger UI закрыть через VPN или Basic Auth

## 6. Дополнительно: Алертинг
На базе OpenTelemetry Collector настроим генерацию метрик из спанов
Если спан "Processing Order" длится дольше 30 минут отправляем алерт в Grafana Alertmanager
